# Exercise 05 evidence: investigate a DNS or TLS failure

Date: 2026-10-13

## 1. Setting and prediction

This is the **supplied simulation**, not my real system. The hostnames, IP
addresses, commands, and outputs below are invented for the lab. I did not run
any of them, and I did not touch my real DNS records or certificates.

The failed check is an HTTPS request to `site.lab.example`.

Prediction: `site.lab.example` should reach the Railway deployment over valid
HTTPS.

## 2. Failed check and evidence

Simulated output, quoted from the exercise:

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

Actual result (simulated): the name resolved to an A record at
`198.51.100.24`, the server there presented a certificate for
`old-vm.lab.example`, and curl stopped with error 60.

## 3. Diagnosis

The dig lookup returned an A record for site.lab.example pointing to
198.51.100.24, the old Azure VM. curl connected to that IP on port 443, but
the server presented a certificate for old-vm.lab.example, so curl rejected it
with error 60, a name mismatch. DNS comes first, and it is the step that
failed: the old VM showed its own certificate correctly, but the record sent
the client to the wrong server. What remains uncertain is whether Railway will
present a certificate for site.lab.example. I can predict it will, but at this
point I can’t know it.

## 4. Repair and repeated check

My proposal, written before seeing the follow-up:

> I propose replacing the A record with a CNAME pointing to
> `current-app.up.railway.app` (DNS only, no proxy). Then clients should reach
> Railway, which should serve a certificate that matches `site.lab.example`.

The change shown is the A record for site.lab.example replaced by a CNAME to
current-app.up.railway.app. This matches my proposal and supports my
diagnosis, because changing only the DNS record fixed the result. The repeated
check shows the CNAME, then the IP 203.0.113.44, a certificate with
CN=site.lab.example, verification ok, and HTTP/2 200. I read this output but
did not run it myself. It confirms the certificate prediction from section 3.

Simulated follow-up output, quoted from the exercise:

## 5. What you learned

I learned to check whether DNS or the certificate failed first, since a curl
error can make them look alike. One check that separates them is
`openssl s_client -connect <ip>:443 -servername site.lab.example`, which skips
DNS and shows the certificate a server presents. It has to be run against the intended
destination, Railway’s IP. If that server presents the right certificate, TLS
is fine and DNS was the fault. A 200 response also doesn’t prove the database
content works, so that needs its own test.
