# Exercise 05 evidence: investigate a DNS or TLS failure

Date: 2026-10-13

## 1. Setting and prediction

This is the **supplied simulation**, not my real system. The hostnames, IP
addresses, commands, and outputs below are invented for the lab. I did not run
any of them, and I did not touch my real DNS records or certificates.

The failed check is an HTTPS request to `site.lab.example`.

Prediction: `site.lab.example` should reach the Railway deployment over valid
HTTPS.

## 2. Failed check and evidence

Simulated output, quoted from the exercise:

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

Actual result (simulated): the name resolved to an A record at
`198.51.100.24`, the server there presented a certificate for
`old-vm.lab.example`, and curl stopped with error 60.

## 3. Diagnosis

The problem started with DNS. `site.lab.example` still had an A record
pointing at the old Azure VM (`198.51.100.24`), so the browser was sent to the
wrong server. The certificate error was a side effect of that. The old server
presented its own certificate (`old-vm.lab.example`), which doesn't match
`site.lab.example`, so curl rejected it.

What remains uncertain: whether Railway serves a certificate that matches
`site.lab.example`. The failed check never reached Railway, so that isn't
known until the follow-up shows it.

## 4. Repair and repeated check

My proposal, written before seeing the follow-up:

> I propose replacing the A record with a CNAME pointing to
> `current-app.up.railway.app` (DNS only, no proxy). Then clients should reach
> Railway, which should serve a certificate that matches `site.lab.example`.

Simulated follow-up output, quoted from the exercise. I interpreted this
output; I did not run it.

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

The change shown is the A record replaced by a CNAME to
`current-app.up.railway.app`.

| | First check | Repeated check |
| --- | --- | --- |
| DNS answer | A `198.51.100.24` | CNAME `current-app.up.railway.app`, then A `203.0.113.44` |
| Connected address | `198.51.100.24` | `203.0.113.44` |
| Certificate name | `old-vm.lab.example` | `site.lab.example` |
| Result | curl error 60 | verify ok, `HTTP/2 200` |

This matches my proposal. DNS was the first fault, and the certificate error
went away once DNS pointed at Railway, without any change to a certificate.

## 5. What you learned

Another check that separates a DNS problem from a TLS problem is to choose the
server yourself, so DNS is out of the picture:

- `openssl s_client -connect <address>:443 -servername site.lab.example`
  connects to an address I pick and shows the certificate that server
  presents for that name.
- `curl --resolve site.lab.example:443:<address> https://site.lab.example/`
  makes the same HTTPS request against an address I pick.

If the right server presents the right certificate this way while the normal
request still fails, the fault is in DNS. If it presents the wrong certificate
even when I connect to it directly, the fault is in TLS on that server. I did
not run either command here.

Also, a 200 over HTTPS does not prove the database content works. It shows
that the name, the route, and the certificate are right, so the page's data
still has to be read and checked.
